## Purpose

チャットの自然言語メッセージからイベントを検索・特定し、予定案としてユーザーに提示、承認後にカレンダーへ登録する一連の対話フローを提供する。会話履歴と予定案の状態を永続化する。

## Requirements

### Requirement: チャットメッセージの受付と会話の永続化

システムはユーザーからのチャットメッセージを受け付け、単一の連続した会話スレッドとしてメッセージ（message）をDBに永続化しなければならない（SHALL）。単一ユーザー・単一カレンダー前提のため、明示的なユーザー識別子や複数スレッドの管理は不要とする。チャットアシスタントは予定（イベント）の検索・登録を目的としたものであり、その役割の範囲で応答する。

#### Scenario: メッセージ送信で単一スレッドに追記される

- **WHEN** ユーザーがチャットメッセージを送信する
- **THEN** システムは単一の連続スレッドにユーザーメッセージとアシスタント応答を時系列で保存する

#### Scenario: 初回メッセージでスレッドが初期化される

- **WHEN** まだ会話が存在しない状態で最初のメッセージを送信する
- **THEN** システムは単一スレッドを初期化してメッセージを保存する

#### Scenario: 会話履歴を取得する

- **WHEN** クライアントが会話履歴の取得を要求する
- **THEN** システムは単一スレッドの全メッセージを時系列順に返す

#### Scenario: 予定登録の役割外のメッセージ

- **WHEN** ユーザーが予定登録と無関係な内容を送信する
- **THEN** システムは予定登録を目的としたアシスタントである旨を案内し、予定案は生成しない

### Requirement: LLMとweb検索によるイベント特定

システムはユーザーメッセージを、設定で選択された LLM プロバイダ（既定は DeepSeek、切替で Claude）で解釈し、web 検索の結果に基づいてイベント情報（名称・開催日時・場所・概要・情報源URL）を抽出しなければならない（SHALL）。DeepSeek 経路では、システムがユーザーメッセージから文脈（年・場所など）を補って検索クエリを組み立て、外部検索を実行したうえで、その結果をコンテキストとして LLM に渡してイベントを抽出しなければならない（SHALL）。抽出結果は予定案（event proposal）として構造化された形で保持しなければならない（SHALL）。抽出される日時は日本標準時（Asia/Tokyo, UTC+09:00）を基準として解釈しなければならず（SHALL）、相対的な日付表現（「今日」「今年」など）は日本標準時の現在時刻を基準に解決しなければならない（SHALL）。予定案の名称・概要・ユーザーへの応答メッセージは、情報源が他言語であっても日本語で提示しなければならない（SHALL）。LLM プロバイダの切替は、以下のシナリオで規定される外部から観測可能なイベント抽出の振る舞い（結果の種別と予定案の構造）を変えてはならない（SHALL NOT）。

#### Scenario: イベントが特定できた場合、予定案を生成する

- **WHEN** ユーザーが「TGSの予定を追加して」のようにイベント登録を意図したメッセージを送る
- **THEN** システムはweb検索の結果に基づいてイベント候補を特定し、名称・開催日時・場所・概要・情報源を含む予定案を生成して未承認（pending）状態で保存し、ユーザーに提示する

#### Scenario: 開催期間が複数日のイベント

- **WHEN** 特定したイベントが複数日にわたる開催期間を持つ
- **THEN** 予定案は開始日時と終了日時の両方を保持する

#### Scenario: 終日・複数日イベントの日付が日本標準時で保たれる

- **WHEN** 特定したイベントが終日（all-day）かつ複数日にわたり、日本標準時で「初日〜最終日」の開催期間を持つ
- **THEN** 予定案の開始日時は初日、終了日時は最終開催日（当日）を指し、日本標準時での表示において日付が前後にずれない

#### Scenario: 情報源が他言語でも日本語で提示する

- **WHEN** イベントの情報源が日本語以外（例: 英語）で記述されている
- **THEN** システムは予定案の名称・概要およびユーザーへの応答メッセージを日本語で提示する

#### Scenario: 初回検索で特定できない場合は限定的に再検索する

- **WHEN** 初回の検索結果からイベントを特定できない、または情報が不十分である
- **THEN** システムは最大1回だけ検索クエリを見直して再検索する

#### Scenario: イベントが特定できない場合

- **WHEN** 再検索を含めてもメッセージから対象イベントを特定できない、または検索で十分な情報が得られない
- **THEN** システムは予定案を生成せず、特定できなかった旨と追加情報を求める応答を返す

#### Scenario: 候補が複数ある場合の確認

- **WHEN** 検索結果として複数のイベント候補が存在する
- **THEN** システムは候補を提示し、どれを登録するかユーザーに確認を求める

#### Scenario: LLMプロバイダを切り替えても抽出の振る舞いは同一の契約に従う

- **WHEN** 設定で LLM プロバイダを DeepSeek と Claude の間で切り替える
- **THEN** 同一入力に対するイベント抽出の観測可能な結果（status の種別と予定案の構造）は同一の契約に従う

### Requirement: 予定案のユーザー確認と承認フロー

システムは生成した予定案をユーザーに提示し、ユーザーの承認を得るまでカレンダーに登録してはならない（SHALL NOT）。ユーザーは予定案を承認・却下でき、承認された場合のみカレンダーに登録される（SHALL）。

#### Scenario: 予定案を承認するとカレンダーに登録される

- **WHEN** ユーザーが提示された予定案を承認する
- **THEN** システムは予定案の内容でカレンダーイベントを作成し、予定案の状態を承認済み（approved）に更新し、作成されたイベントを返す

#### Scenario: 予定案を却下する

- **WHEN** ユーザーが予定案を却下する
- **THEN** システムはカレンダーへの登録を行わず、予定案の状態を却下（rejected）に更新する

#### Scenario: 承認前は登録されない

- **WHEN** 予定案が生成された直後（未承認）の状態である
- **THEN** 対応するカレンダーイベントは存在しない

#### Scenario: 承認前の予定案を編集して承認する

- **WHEN** ユーザーが予定案の日時・場所などを修正したうえで承認する
- **THEN** システムは修正後の内容でカレンダーイベントを作成する

#### Scenario: 処理済みの予定案は再承認できない

- **WHEN** 既に承認済みまたは却下済みの予定案に対して再度承認を要求する
- **THEN** システムはエラーを返し、重複したカレンダー登録を行わない

### Requirement: 会話スレッドのクリア

システムは単一の会話スレッドをクリアする操作を提供しなければならない（SHALL）。クリアはスレッドに属するすべてのメッセージおよび予定案を削除し、以降のメッセージ送信は空の状態から開始しなければならない（SHALL）。単一ユーザー・単一カレンダー前提のため、クリア対象のスレッド指定は不要とする。

#### Scenario: 会話をクリアするとメッセージと予定案が削除される

- **WHEN** クライアントが会話のクリアを要求する
- **THEN** システムはスレッドの全メッセージと全予定案を削除し、成功を返す

#### Scenario: クリア後の会話履歴取得は空を返す

- **WHEN** クリア後にクライアントが会話履歴の取得を要求する
- **THEN** システムはメッセージと予定案が空の会話を返す

#### Scenario: クリア後も新規メッセージを受け付ける

- **WHEN** クリア後にユーザーがメッセージを送信する
- **THEN** システムは空の状態から会話を再開し、メッセージを保存して応答する

### Requirement: LLMへ渡す会話履歴の上限

システムはイベント特定のために LLM へ渡す会話履歴を直近の一定件数（ターン数）に制限しなければならない（SHALL）。会話が長くなっても LLM へ送信するコンテキスト量が履歴全体に比例して際限なく増加してはならない（SHALL NOT）。永続化される会話履歴自体はクリアされない限り保持する（この上限は送信範囲にのみ適用される）。

#### Scenario: 履歴が上限を超えても直近のみ送信する

- **WHEN** 会話履歴が上限ターン数を超えた状態で新しいメッセージを送信する
- **THEN** システムは直近の上限ターン数ぶんの履歴のみを LLM へ渡してイベント特定を行う

#### Scenario: 上限以内の履歴はそのまま送信する

- **WHEN** 会話履歴が上限ターン数以内の状態でメッセージを送信する
- **THEN** システムは既存の履歴をすべて LLM へ渡す
